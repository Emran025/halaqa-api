# تدقيق اكتمال عقد OpenAPI

## الحكم الحالي

بعد إضافة نموذج التسجيل الموسع، أصبح العقد يغطي ملف الطالب الشخصي والتواصلي، مستوى الحفظ السابق، خطة الحفظ والمراجعة والتلاوة، تكرار الخطة، أوقات الحضور، كود المعلم الاختياري، صندوق الطلبات العامة، قواعد إخفاء البيانات، ملف المعلم ومؤهلاته، الجدولة وقائمة المتابعة، وسجلات الحضور اليومية.

تم التحقق آليًا من صحة OpenAPI 3.1.1، ويحتوي العقد حاليًا على 66 مسارًا و90 عملية و142 مخططًا. تثبت هذه النتيجة صحة البنية وتغطية العمليات والمراجع، بينما توثق الأقسام التالية قرارات المجال المثبتة ومتطلبات التنفيذ المتبقية.

## الحقول التي أضيفت وحُسمت

| المجال | الحقول والعقد |
|---|---|
| حساب الطالب | الاسم، اسم المستخدم الاختياري، البريد، كلمة المرور، الجنس، تاريخ الميلاد، الدولة، المدينة، السكن، الهاتف، رمز الدولة، WhatsApp ورموزه. |
| الحفظ السابق | مستوى الحفظ، مستوى المراجعة، عدد الأجزاء، السور المحفوظة، آخر وحدة مكتملة، وملاحظات المعلم السابق. |
| خطة الطالب | التكرار اليومي أو الأسبوعي أو مرتين أو ثلاث مرات أسبوعيًا، تفاصيل نوع المهمة والوحدة والكمية، تاريخ البداية والنهاية. |
| حضور الطالب | المنطقة الزمنية، أيام الأسبوع، من وإلى، الفترة المفضلة، ومدة الجلسة المفضلة. |
| توجيه الطلب | `teacher_code` اختياري، و`routing_mode` بقيمتي `specific_teacher` أو `all_available_teachers`. |
| خصوصية المتقدم | `ApplicantPublicSummary` قبل القبول، مع منع البريد والهاتف وWhatsApp والخطة وأوقات الحضور والبيانات التفصيلية. |
| ملف الطالب بعد العلاقة | البيانات الشخصية والتواصل والحفظ السابق والخطة وأوقات الحضور، ولا يعرض إلا للطالب نفسه والمعلم المرتبط. |
| المعلم | البيانات الشخصية والتواصل، المؤهل، سنوات الخبرة، السيرة، القدرة الاستيعابية، الحلقات، والوثائق. |
| وثيقة المعلم | نوع الشهادة، النوع الآخر، الرواية، جهة الإصدار، تاريخ الإصدار، رابط الملف، وحالة وجود الملف. |
| الجدولة | عنصر متابعة مرتبط بالطالب والخطة ونوع المهمة، الموعد، المنطقة الزمنية، الحالة، الإنجاز، التجاوز، إعادة الجدولة والتنبيه. |
| المتابعة اليومية | الحضور، ملاحظة السجل، الملاحظة السلوكية، الوحدات من وإلى، الكمية الفعلية، الحالة، التعليق، الدرجة، الفجوة، والأخطاء. |

## آلية الخصوصية المعتمدة

عند ترك الطالب كود المعلم فارغًا، ينشئ الخادم طلبًا بقيمة `routing_mode: all_available_teachers`. يظهر الطلب في `GET /student-applications` للمعلمين المؤهلين، ولكن الاستجابة تستخدم `ApplicantPublicSummary` فقط. لا يجوز لأي Resource خاص بقائمة المتقدمين إعادة الحقول الحساسة.

عند إدخال كود معلم، يضع الخادم `routing_mode: specific_teacher` ويربط الطلب بالمعلم المطابق. يظل الإخفاء قائمًا حتى القبول. بعد قبول الطلب وإنشاء العلاقة التعليمية، يمكن للطالب ومعلمه المرتبط استخدام `GET /students/{studentId}` أو `GET /me/student-profile` وفق Policy العلاقة. لا يعاد الملف التفصيلي لمعلم آخر لمجرد أن الطالب كان ظاهرًا في قائمة الطلبات العامة.

لا توجد دورة موافقة إدارية في العقد الحالي لإنشاء حساب المعلم. تسجيل المعلم يعيد الحساب والملف التعريفي والقدرة والوثائق وفق `TeacherRegistrationInput`، مع بقاء التحقق من صحة البيانات مسؤولية Laravel Form Request وPolicy المناسبة.

## قرارات المجال المثبتة في العقد الحالي

تم حسم القرارات التالية في OpenAPI وMySQL وعقد الاتصال، ولا ينبغي إعادة فتحها عند بناء التنفيذ إلا عبر تغيير موثق للعقود الثلاثة:

| القرار | القيمة المعتمدة ومصدرها |
|---|---|
| عدد حلقات المعلم | يسمح النظام للمعلم بامتلاك عدة حلقات؛ يضبط العدد الفعلي بواسطة `max_halaqas` وعدد الحلقات الفعالة. |
| نوع الجلسة | الجلسة فردية بين معلم وطالب واحد؛ يعكس ذلك `teacher_id` و`student_id` وقناة الطرفين في MySQL وWebRTC. |
| عضوية الطالب | يمكن حفظ تاريخ عضويات متعددة، لكن لا توجد إلا عضوية فعالة واحدة للطالب في النطاق الحالي، ويمنعها القيد `uq_active_student_membership`. |
| دورة الخطأ | الخطأ المسجل عبر REST يصبح سجلًا رسميًا قابلًا للتعديل أو الحذف المنطقي قبل اكتمال التقرير وفق Policy؛ العرض اللحظي مؤقت ولا يستبدل الحفظ الرسمي. |
| دورة التقرير | اعتماد المعلم ينقل التقرير إلى `pending_student_acknowledgment`، وتأكيد الطالب ينقله إلى `completed`، وإعادة الفتح تنقله إلى `reopened` مع سبب إلزامي. |
| سلم التقييم | درجة صحيحة من 0 إلى 100 للمعلم وللطالب، مع سجل تقييم واحد لكل مقيم لكل مهمة. |
| سياسة الاتصال المباشر | Host ICE فقط دون STUN/TURN/Relay؛ فشل الاتصال يسجل `direct_connection_unavailable` ولا ينشئ مسارًا بديلًا. |

## قرارات تنفيذية يجب تثبيتها قبل الإنتاج

لا توجد فجوات بنيوية في العقد الحالي، لكن يجب تحويل القرارات التالية إلى إعدادات موثقة واختبارات قبل إطلاق التنفيذ:

| القرار التنفيذي | المطلوب تثبيته |
|---|---|
| التنبيهات | جدول أوقات التنبيه قبل الموعد وبعد تحوله إلى `overdue`، مع اعتماد الإشعار الداخلي وقناة WebSocket عند الجلسة. |
| إعادة الجدولة | تحديد ما إذا كان تغيير الموعد يحتاج قبول الطرف الآخر، مع إبقاء Policy وAudit Event مصدر القرار. |
| الاحتفاظ بالبيانات | مدة الاحتفاظ ببيانات التواصل والوثائق وسجلات التدقيق، مع عدم التأثير في السجل التعليمي المعتمد. |
| فشل P2P | عدد محاولات إعادة التفاوض وزمن الانتظار قبل تسجيل الفشل النهائي، دون إضافة Relay أو خادم وسيط. |
| مصدر المصحف | تثبيت إصدار المصحف الافتراضي وآلية Seed/Import والتحقق من سلامة العلاقات بين الإصدار والسور والآيات والصفحات. |

## ملاحظات تقنية على العقد

لا يصف OpenAPI WebSocket بصورة معيارية كاملة، لذلك يوجد `REALTIME_CONTRACT.md` لعقد القنوات والأحداث. إذا كان المطلوب توليد كود WebSocket آليًا، ينبغي إضافة ملف AsyncAPI مستقل.

يجب أن تكون الاستجابات الفعلية في Laravel مطابقة لمخططات `Resource`، وأن تكون الحقول المخفية ناتجة عن Projection أو Resource مختلف، لا عن إرسالها ثم الاعتماد على إخفائها في تطبيق WPF. ويجب استخدام `Idempotency-Key` أو `client_operation_id` في إنشاء الطلبات، إعادة الجدولة، وتسجيل العمليات التي يمكن تكرارها بسبب إعادة الاتصال.

## الخلاصة

بعد المراجعة، أصبح العقد **متكاملًا وظيفيًا ومعماريًا ضمن النطاق الحالي**، ويغطي بيانات الطالب والمعلم والطلبات العامة وكود المعلم والخصوصية والخطة الدورية والجدولة والتنبيهات وقائمة المتابعة والمصحف والجلسات الفردية والتقارير والاعتمادات. تبقى الجاهزية الإنتاجية مشروطة بتحويل قرارات التنفيذ الموثقة إلى Laravel Migrations وForm Requests وPolicies وServices وResources واختبارات النجاح والفشل والصلاحية والتكرار وفشل الاتصال المباشر.


## تدقيق صراحة عقد API

في الإصدار الحالي لا تحتوي مخططات الطلبات والاستجابات على خاصية عامة باسم `data`. تستخدم الاستجابات أسماء دلالية صريحة مثل `user`, `student_profile`, `teacher_profile`, `registration_request`, `sessions`, `tasks`, `mistakes`, `report`, `progress`, `notifications`, و`realtime_session`. كما تستخدم موارد المصحف `edition_id` و`page_number` و`ayah_id` الرقمية بصورة صريحة.

أغلقت مخططات الأجسام العلوية والمتداخلة باستخدام `additionalProperties: false`، مع إبقاء فروع `allOf` الجزئية مفتوحة فقط لأنها امتدادات موروثة وليست أجسامًا مستقلة. كما أضيف `NotificationPayload` و`ErrorDetails` و`FieldValidationError` و`ProgressTotals` كمخططات صريحة بدل الخرائط العامة.

نتيجة الأدوات: **90 عملية، 38 جسم طلب، 80 استجابة JSON، 142 مخططًا، 122 مخطط كائن، صفر خصائص data، صفر أجسام ديناميكية غير مبررة، وصفر مراجع داخلية مفقودة**. العمليات الجزئية مثل PATCH لا تضع كل الحقول في `required` لأنها تقبل تحديث حقل واحد، لكنها تستخدم `minProperties: 1` أو حقلاً إلزاميًا للعملية مثل `client_operation_id` و`reason`. العمليات الإنشائية القابلة لإعادة المحاولة تستخدم `client_operation_id`، بينما تعتمد العمليات التي لا تحمل جسمًا على `Idempotency-Key` في طبقة HTTP عند تنفيذها.
